## Context

当前选座系统基于 MySQL 位图模型，通过 CAS 乐观锁逐个锁定座位。选座时只按座位类型分组，随机分配座位，不支持用户选择具体位置，也不保证同一订单的乘客座位相邻。

核心约束：
- 座位表结构：t_seat 包含 train_id, carriage_number, seat_number, seat_type, seat_bitmap
- 座位号格式：seat_number = "01A" (排号+位置), carriage_number = "05" (车厢号)
- 并发控制：当前使用 CAS 乐观锁 (UPDATE WHERE (seat_bitmap & ?) = 0)
- 缓存策略：余票缓存 1 分钟，选座后删除缓存

## Goals / Non-Goals

**Goals:**
- 支持用户选择位置偏好 (A/B/C/D/F)
- 同一订单乘客优先分配同一排连续座位
- 支持跨车厢选座降级
- 保持并发安全 (分布式锁)
- 保持现有 API 兼容性 (chooseSeats 可选)

**Non-Goals:**
- 不支持用户指定具体排号
- 不修改座位表结构
- 不改变现有座位类型体系
- 不实现实时座位可视化

## Decisions

### Decision 1: 选座算法采用内存矩阵 + 降级策略

**选择**: 查询数据库后构建内存矩阵，在内存中运行选座算法

**替代方案**:
- 方案A: 纯 SQL 查询连续座位 → 实现复杂，难以支持复杂偏好
- 方案B: Redis BitMap + 内存矩阵 → 增加缓存复杂度，一致性难保证

**理由**:
- 内存矩阵算法简单清晰，易于实现和维护
- 座位数量有限 (单列车最多 1000+ 座位)，内存占用可控
- 在分布式锁保护下，无需担心并发问题

### Decision 2: 分布式锁粒度为 trainId + seatType

**选择**: 锁 key = "seat:train:{trainId}:type:{seatType}"

**替代方案**:
- 方案A: 粗粒度锁 (trainId) → 并发度低
- 方案B: 细粒度锁 (trainId + carriageNumber) → 实现复杂，跨车厢选座需多锁

**理由**:
- 同一订单只能选择一种座位类型，不同类型之间互不影响
- 中粒度锁平衡并发度和实现复杂度
- 选座操作耗时短 (毫秒级)，锁竞争可接受

### Decision 3: 偏好处理策略

**选择**: 偏好只在第一个车厢尝试，后续车厢不再考虑

**替代方案**:
- 方案A: 所有车厢都尝试满足偏好 → 可能导致跨车厢分散
- 方案B: 偏好作为权重，优先但不强制 → 实现复杂

**理由**:
- 跨车厢已无法实现"同一排"，偏好意义不大
- 优先保证"有座位"，而非"满足偏好"
- 实现简单，用户体验可接受

### Decision 4: 选座算法降级优先级

**选择**: 同排+偏好 → 同排连续 → 同排分散 → 跨车厢

**理由**:
- 优先满足用户偏好 (同排+指定位置)
- 其次保证座位连续 (便于交流)
- 再次保证同排 (至少同一排)
- 最后跨车厢降级 (保证有座位)

### Decision 5: 批量锁定采用逐条 CAS

**选择**: 对选中的座位逐条执行 CAS 更新

**替代方案**:
- 方案A: 单条 SQL 批量更新 → 难以保证原子性
- 方案B: 事务 + 行锁 → 可能死锁

**理由**:
- 在分布式锁保护下，CAS 更新应该总是成功
- 逐条 CAS 保持与现有代码一致性
- 实现简单，性能可接受

## Risks / Trade-offs

**Risk 1: 高并发时锁等待**
- 影响: 同一列车同一座位类型的选座请求串行执行
- 缓解: 选座操作耗时短 (10-50ms)，锁竞争可接受
- 监控: 观察锁等待时间和失败率

**Risk 2: 内存占用**
- 影响: 构建内存矩阵需要额外内存
- 缓解: 单列车座位数有限 (最多 1000+)，内存占用可控
- 监控: 观察 JVM 内存使用情况

**Risk 3: 选座算法性能**
- 影响: 遍历所有排/列寻找连续座位，时间复杂度 O(rows * cols)
- 缓解: 座位数量有限，算法耗时短
- 优化: 可提前终止，找到即返回

**Risk 4: 跨车厢选座用户体验**
- 影响: 跨车厢时乘客座位分散
- 缓解: 优先在同一车厢分配，无法满足时才跨车厢
- 说明: 这是业务规则的权衡，保证有座位 > 座位集中

## Migration Plan

**部署步骤**:
1. 部署新代码 (向后兼容，chooseSeats 可选)
2. 验证新功能正常工作
3. 前端逐步上线选座界面

**回滚策略**:
- 代码回滚: 移除 chooseSeats 参数处理，恢复原有选座逻辑
- 数据回滚: 无需数据迁移，回滚无风险

**监控指标**:
- 选座成功率
- 锁等待时间
- 跨车厢选座比例
- 用户偏好分布

## Open Questions

1. **座位号解析**: 已确认格式为 "01A" (排号+位置)，位置占最后一个字符
2. **位置映射**: 已确认从数据库读取的数据动态确定，不硬编码
3. **偏好数量**: 已确认前端限制偏好数 <= 乘客数，后端也做校验
4. **跨车厢策略**: 已确认优先同一车厢，无法满足则跨车厢降级
